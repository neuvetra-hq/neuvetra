## Recorded execution sequence and interfaces

These functions in [website-publication.ts](website-publication.ts) describe the completed first-run flow, executed through the separately reviewed private coordinator wrapper. They are not instructions to repeat migration or activation against the now-active C scope. Imports perform no I/O. There is no CLI that loads an environment export. Credentials are in-memory arguments; never put their values in arguments, logs, tracked files or public receipts. Reserve unique private output/journal paths before any live operation, pin the code and inputs, and record each operation's outcome separately. The safe journal must finish synchronously (for example, a protected `writeFileSync` wrapper); Promise/thenable callbacks are refused before the next provider call. No automatic retries or cleanup exist.

1. **Review target and inventory.** Confirm the exact shared Supabase project and Pinecone host/profile. Obtain and pin a successful current read-only direct database inventory with the official CA. The database factory must use `directWriteOptions` from the existing apply helper and retain certificate verification; no pooled or alternative-project fallback. The target must bind the release, canonical plan hash, fixed scope/build/profile/namespace and explicit review deadline. `preflight(input)` checks it without I/O. Root chose the source deadline, September 15, 2026 at 23:20:32 UTC; the older synthetic target expiry is unchanged.
2. **Extend checks once.** Call `applyWebsiteScopeMigration(migrationBytes, MIGRATION_SHA, directFactory)`. It validates the exact migration bytes before creating a client, checks the live read-only TLS session, then sends the unchanged full `BEGIN`/`COMMIT` script once with its fixed project acknowledgement. The SQL requires the private bucket and expected constraint names. The committed migration receipt above now records this first-run success; keep the pinned SQL bytes unchanged.
3. **Stage pending rows.** Call `stageWebsite(input, directFactory)`. `input` contains `{release, releasePin, target, targetPin, now}`. This stages exactly 25 rows in one transaction: one scope, three objects, one source, one release, eighteen passages and one ingestion run. Source/passages are pending, release candidate, run staged; there is no membership or pointer write. Existing identical rows are compared in full; any conflict refuses rather than overwriting. JSON binds as text before conversion to JSONB.
4. **Publish immutable files and selected text.** Call `createWebsiteTransport(input, {supabaseAdminKey, pineconeApiKey})`, then `publishWebsite(publicationInput, transport, safeJournal)`. `publicationInput` adds `{objects: {source, extraction, release}, stageReceipt, stageReceiptPin}`. It requires the exact successful stage receipt and rechecks all original/extraction/passage hashes and spans before any transport. Files are copied to prevent mutation during awaits. The transport permits only the fixed reviewed object paths and exact object bytes, fixed index description, exact 18-record upsert body and exact vector fetch IDs. It uses direct verified HTTPS without proxies, redirects or retries. Modern secret API keys use `apikey` without a non-JWT Bearer value.
5. **Verify separately.** Call `verifyWebsitePublication` with the same inputs and a new journal. This performs only GET requests, verifies three object hashes/sizes, fetches all eighteen vector IDs and checks their exact metadata and finite 1024-dimensional values. An upload response is not readiness proof. If visibility is delayed, a separately authorized bounded verification attempt can inspect it; do not repeat publication just to poll. Supabase HTTP 400 counts as a missing object only with the bounded `404`/`NoSuchKey` response shape. Incompatible buckets, generic 400s and other failures withhold publication success.
6. **Provide the dedicated reader.** Root separately creates and signs in the private `.invalid` account; this helper does not create/list/delete users. Its email is `neuvetra-website-epa-20260909@neuvetra.invalid`. Expected Auth app metadata is `{scope_id: "90000000-0000-4000-8000-00000000000c", run_marker: "neuvetra-website-epa-20260909", kind: "private_research_reader"}`. The pinned safe identity receipt must include `{project_ref, run_id: "neuvetra-website-epa-20260909", scope_id, email, status: "signed_in", auth_user_id, expires_at}`; expiry is Unix seconds. Passwords and tokens are excluded from that receipt.
7. **Activate only after verified readback.** Call `activateWebsite({...input, publicationReceipt, publicationPin, identityReceipt, identityPin}, directFactory)`. The readback must be complete, exact and no more than 30 minutes old. The transaction locks the isolated research tables, compares all 25 pending rows, refuses a prior C membership/pointer, and checks only the supplied Auth UUID's confirmed role/email/app metadata. It then creates one membership, applies the separately reviewed source disposition to the fixed projection, marks the run verified and invokes the existing activation RPC for C. No A/B scope enters these updates. Commercial approval remains false.
8. **Verify the actual website separately.** Bind the final target, reader UUID and release to the cloud repository. Confirm authorized source resolution, cross-scope denial, displayed PDF citations and complete, qualified answers through the real website. Source and publication success do not substitute for those checks.

Publication and database commits are not one cross-provider transaction. A lost response can leave an uncertain outcome. Preserve the journal and use a fresh read-only inspection before deciding whether another attempt is appropriate; never blindly repeat activation or reset approved rows. These functions do not revoke/deactivate/delete resources, change application routes, guarantee answer quality or clear public/commercial rights.
