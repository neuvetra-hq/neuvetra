## Baseline observations and design challenges

1. `apps/site-api/src/workspace/server.ts` creates an in-memory PGlite database and authenticates fixed bearer strings. The entry point is explicitly development/test only. Its calculation-flight map is process-local. These controls must remain confined to the local demo; changing flags alone is not hosted productionization.
2. `packages/neuvetra-database/src/index.ts:312` scopes the claimed actor and `authenticated` role to a transaction for ordinary reads. The adjacent `asTrustedUser` path retains the database owner privilege for writes. Hosted request execution must not keep an owner, superuser, BYPASSRLS, or broadly privileged service credential; a startup role assertion alone is insufficient if the login can later assume a privileged role. Dedicated narrow functions need individually reviewed grants and owner privileges.
3. `0001_company_workspace.sql` grants the `authenticated` role access to `create_company_workspace`; the function requires only a nonnull `auth.uid()`. Invitation gating must apply to every externally reachable creation path, including direct database/RPC access where exposed. User metadata and client-supplied roles are not membership authority.
4. The legacy `packages/frontdesk-database/migrations/0007_neuvetra_namespace_reorg.sql` grants authenticated schema access and broad default table privileges in product schemas. This source is not proof of live exposure, but neither the schema separation nor Neuvetra RLS proves safety of a shared Supabase identity tenant. Verify legacy grants, RLS and exposed API schemas without querying customer rows, or use a separately isolated staging identity/data project.
5. Existing evidence-pack/report readers reconstruct semantic lineage and exact bytes. Hosted persistence must preserve these checks and pinned methods. PostgreSQL timestamp/bytea/JSON representation and transaction concurrency differ from the local adapter and require direct tests.
