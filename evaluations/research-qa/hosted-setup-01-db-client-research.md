# HOSTED-SETUP-DB-CLIENT-RESEARCH-01 — timeout and transaction ownership

Date: 2026-09-26. Independent QA/security research for CTO/CEO. No product code, packages, configuration, ENV, secrets, provider or database state changed. This assessment reads installed source, prior native evidence and primary upstream material; no new native test was run. Requested critical gpt-6-astra/high; observed settings unavailable.

## Recommendation

Build a **dedicated, single-use `pg.Client` adapter for the maintenance transaction**, with explicit transaction control and no pool, reconnection or reuse. Keep the exact current Bun runtime as the first compatibility candidate and require the native tests below before acceptance. Changing only the library is insufficient: the adapter must permanently revoke callback SQL access when its transaction ends or fails.

Separately remediate the shared application's transaction adapter: the installed reservation defect is relevant to tenant isolation too. Do not disguise a broad application-driver replacement as a migration-only fix, or regard the maintenance adapter as closing the application's risk.

Node-postgres documents explicit BEGIN/COMMIT/ROLLBACK on one client and prohibits spreading a transaction across pool.query calls. Bun's documentation lists pg as usable, but that is not evidence for this exact forced-timeout lifecycle. [Transaction contract](https://node-postgres.com/features/transactions), [Bun SQL documentation](https://bun.com/docs/runtime/sql).

## Evidence: observed versus inferred

**Locally reproduced in preceding QA:** PostgreSQL 17.11 terminated both an idle-callback and repeated-short-query transaction at the 1.2-second test budget; exact schema-22 state and released locks were confirmed. Installed postgres 3.4.9 under Bun 1.3.12 emitted an uncaught `socket.write` null error during each teardown. The decisive harness finished explicit shutdown but exited 1. This is preserved in `hosted-setup-01-transaction-sequence-independent-review2.md`, SHA `420255755be40f095565c20a393ae4f827934b8a6698463cd09e0d7c3dc6761c`.

**Installed-source explanation:** `postgres/src/index.js` begin races its still-running callback against connection close. Its catch path later attempts ROLLBACK. Pool onclose clears the reservation, moves the connection to the closed queue and can reconnect for waiting work. `connection.js` clears socket to null; `nextWrite` dereferences socket. This supports a late-callback/lifecycle hazard; it is not a complete proof of every internal event ordering behind the native error.

**Upstream #1189 is material and source-confirmed, but its trigger was not independently reproduced here.** The installed execute function writes protocol bytes before short-circuit conditions for backpressure/pipeline capacity and the onexecute reservation hook. Thus an accepted BEGIN can precede a skipped reservation. The issue reports orphaned transactions and subsequent caller reuse on PostgreSQL 17/Node. `max: 1` does not cure that reported case. Linked PR #1218 is still open as read today; neither an open patch nor setting max_pipeline to zero is an accepted fix. [Issue #1189](https://github.com/porsager/postgres/issues/1189), [proposed fix #1218](https://github.com/porsager/postgres/pull/1218).

The reservation defect is distinct from F07's observed timeout teardown error. Both make the current transport unsuitable for acceptance without repair; do not claim that #1189 itself caused the reproduced timeout error.

## Concrete maintenance adapter contract

This is the proposed implementation contract, not an implemented guarantee:

1. Construct one explicit client with pinned connection identity, verified TLS/CA, bounded connection time, explicit configuration and no implicit credential/ENV fallback. Attach nonthrowing error/end listeners before connecting. Pin the exact package/transitive/runtime versions in the reviewed source closure. Use ordinary sequential queries, with pipeline mode disabled where supported.
2. Arm and read back the session's PG17 transaction_timeout before BEGIN, then execute BEGIN ISOLATION LEVEL READ COMMITTED and verify timeout/isolation on that client. Keep the runner's in-transaction setting/readback too. Record backend identity for diagnostics/resolution. Server transaction_timeout terminates the session, rather than merely cancelling one statement. [PostgreSQL 17 timeout semantics](https://www.postgresql.org/docs/17/runtime-config-client.html#GUC-TRANSACTION-TIMEOUT).
3. Give the runner only an immutable transaction-scoped wrapper with a private active-generation flag. Every query/exec checks the flag immediately before dispatch. Reject concurrent transaction requests, root-connection queries during an active transaction, and post-callback SQL. Track in-flight operations so an unawaited query cannot outlive callback completion into COMMIT. Only the adapter sends physical BEGIN/COMMIT/ROLLBACK; the existing migration same-transaction wrapper must not open another transaction.
4. On callback failure, fatal client error, end or deadline, revoke the generation synchronously. Observe all already-created promise rejections. Roll back only if the original client remains alive and in a usable transaction; never reconnect to issue cleanup. Close idempotently, never release/reuse this client. A late callback may finish in JavaScript but its SQL capability stays invalid forever. Current upstream pg source marks connection errors non-queryable and rejects later queries, but an adapter-level guard remains necessary. [pg client source](https://github.com/brianc/node-postgres/blob/master/packages/pg/lib/client.js), [client lifecycle/events](https://node-postgres.com/apis/client).
5. Handle a callback that never settles without merely abandoning an active transaction: fatal/deadline handling must revoke access and terminate the client. Run the one-shot task in an isolated worker/process with bounded shutdown so a blocked callback cannot stall the coordinator indefinitely. A supervisor timeout must preserve an uncertain journal, not claim rollback or restart the migration. Do not suppress global unhandled exceptions as a repair.
6. Commit only after callback success, completed queued work, valid generation and final deadline checks. A sent COMMIT followed by disconnect remains uncertain. Reconcile through a new authenticated primary connection after independently establishing original-transaction resolution. Neither a local close acknowledgement nor a missing marker alone authorizes replay.

`pg.Client` has documented disconnect and error events; upstream source prevents reusing an already connected Client. Those mechanisms are promising, not native validation of a selected release under Bun. The upstream master package currently reports 8.23.0; that is not a verified registry release selection. Select and lock a reviewed release during authorized implementation, then test it. [Client source](https://github.com/brianc/node-postgres/blob/master/packages/pg/lib/client.js), [upstream package metadata](https://github.com/brianc/node-postgres/blob/master/packages/pg/package.json).

Do not switch the entire runner to Node without accounting for Bun.CryptoHasher/Bun.file in upgrade, migration and workspace dependencies. If pg under the pinned Bun runtime fails lifecycle tests, a reviewed Node worker is a fallback, requiring either portable dependency changes or a narrowly specified transport boundary and a new source closure. Bun.SQL and pg-native/libpq add different runtime/native assumptions and have no local evidence here; neither is an automatic shortcut. Keeping postgres.js with reserve/manual BEGIN would still require repair of late callback and teardown behavior, so it is not the preferred path.

## WorkspaceConnection and application scope

No public interface expansion is required for the first candidate: `query<T>(text, params) -> {rows:T[]}`, `exec(text)`, `transaction(operation)` and `close()` can wrap pg.Client. Retain parameterization and Uint8Array-to-Buffer handling; exec must accept the reviewed multi-statement migration batch, while query must not silently mis-handle a multi-result array. Preserve SQLSTATE internally and redact query/parameter details from public errors. Revalidate JSON-text fingerprints, numeric/bigint precision, timestamps, bytea and array parameters; do not introduce global lossy parsers. [Query parameter behavior](https://node-postgres.com/features/queries), [type handling](https://node-postgres.com/features/types).

**Shared app risk:** hosted.ts creates its connection through the same postgres.js-backed createPostgresConnection. HostedWorkspaceDatabase.asUser (lines 103–115) sets the transaction-local JWT subject, checks has_staging_access and runs tenant operations inside this.db.transaction; trusted writes use that same boundary. If a physical transaction is orphaned/reused or logical transactions overlap, subject/commit/rollback ownership can be wrong. RLS does not establish which logical caller owns a reused session. This is a material isolation/integrity risk inferred from matching source plus upstream evidence, **not a reproduced cross-tenant disclosure, corruption or observed live incident**.

Track a separate high-priority shared-adapter remediation. A pg pool candidate must acquire one client exclusively before BEGIN, keep every subject/gate/query/COMMIT on it, and destroy the client on uncertain/error paths. Never pool.query a tenant transaction. Healthy reuse requires verified completion and revoked old callback capabilities. Pool documentation supports exclusive acquisition and `release(true)` destruction; test the chosen version rather than assume its guarantees. [Pool API](https://node-postgres.com/apis/pool).

## Required native regression gate

Use disposable PG17 only, exact runtime/driver versions, supervised child exit and a separate observer connection:

- Real schema-22 → 23 on one PID/xid; actual table/sequence locks, baseline and unique receipt. No late or second physical transaction.
- Short server budget: idle callback, repeated short statements, lock wait, long statement and pending final journal. Observe session death/rollback, unchanged fingerprint/sequence state and released locks. Exit cleanly without unhandled errors or orphan listeners.
- Release a retained callback after timeout/rollback/commit; query/exec must reject before any socket write. Test never-settling callback, queued/unawaited work and error/end/close ordering. No reconnect, connection reuse or second migration.
- Inject disconnect before/during/after COMMIT. Verify no automatic retry and correct uncertain classification; primary resolution distinguishes present/missing/wrong marker without false success.
- Reproduce #1189's pipeline-boundary/backpressure trigger against the current driver as a preserved baseline, then show the replacement has exclusive BEGIN ownership even under concurrent root queries and pool exhaustion.
- For the shared app: two synthetic tenants, actual hosted runtime role/RLS/access gate, interleaved reads/writes, different JWT subjects, concurrent successes/refusals and forced disconnects. Verify A never sees/modifies B, one rollback cannot undo another caller's committed work, and a released client has no residual transaction-local subject/role. Exercise pool sizes 1 and greater than 1, late callbacks and outsider requests. These tests are required before claiming tenant isolation restored.
