## Decision

**A complete runtime-observed module graph is not necessary to satisfy the board's safe schema-22 to schema-23 preservation requirement. Replace that candidate contract explicitly with an independently reviewed exact-artifact, controlled-launch contract.** A clean published archive, pinned dependency/runtime artifacts, sanitized fresh process, private pinned SQL and the existing locked single transaction are proportionate under a stated trusted-operator/host assumption. This is a viable design recommendation, not acceptance of a runnable launcher or permission to treat today's refusal candidate as an executor.

The current source lock cannot honestly be supplied fabricated `moduleGraphComplete`, `runtime-loader-observed-v1` or `immutableRuntimeTree` assertions. It must receive a deliberately versioned replacement contract; its historical PASS remains conditional on the old contract. The refusal-only launcher correctly refuses the contract it was given. Its failure to prove an unnecessarily strong boundary is not evidence that safe migration requires a new runtime, complete loader instrumentation, or protection against a hostile host administrator.

**A bare commit string, copied directory, child self-report, or before/after hashes are insufficient.** They identify neither trusted provenance nor the code consumed during a concurrent hostile modification. The retained author counterexample proves this point. This recommendation does not rename those weaker observations as lifetime immutability.

## Trust and threat boundary

The operational host, OS/runtime installation, reviewed supervisor, authenticated publication channel and operator are trusted. The process does not execute user code, tenant uploads, arbitrary plugins or database-derived JavaScript. The release artifact is prepared exclusively by the supervisor, is outside every active development checkout, and is not modified by other agents or package managers during execution. The worker cannot choose a new executable, arbitrary module path or verifier callback through its request data.

This boundary addresses accidental checkout drift, stale/forged launch inputs, inherited environment/config preloads, wrong dependencies, concurrent ordinary database writers, timeouts and uncertain commit. It does **not** claim resistance to arbitrary same-account code injection, a compromised runtime/OS, or hostile provider administrators. That is an explicit operational assumption, consistent with the sequence fence's existing no-concurrent-DDL/security-maintenance condition. Table locks do not freeze every routine/role/catalog change; prohibit concurrent schema/security administration during the window and verify supported database profile/catalog before and after. Do not claim that sampled idle sessions establish this condition mechanically.

If hostile concurrent modification by the host account is part of the required threat model, a clean archive plus process isolation is not sufficient. Then use an independently administered read-only artifact/image or other demonstrated OS separation before execution. Do not simulate that protection with `Object.freeze`, read-only file attributes, a hash, or a cooperative directory convention. Under the ordinary trusted-host maintenance model there is no need to implement that stronger host-adversary gate first.

## Narrow implementation

1. **Authenticate and materialize a release artifact before credentials or application imports.** A reviewed supervisor starts with a pinned runtime executable and a fresh process environment, not an already-running Bun application. Independently authenticate the exact published PR #6 head and required checks. Materialize that commit into a new private absolute directory outside active checkouts. Record archive hash, commit, supervisor/runtime hashes and launch profile. Never overlay working-tree/untracked files. Materialize dependencies from a separately pinned dependency artifact with a complete at-rest file manifest; the Git archive or lockfile alone does not contain their installed bytes. No package installation, lifecycle scripts, cache fallback or network code acquisition during execution. Review the actual installed `pg` resolution and all runtime configuration inputs. Reject symlinks/junctions or resolution paths escaping the artifact. A full shipped-file manifest is artifact inventory, not a claim about every module loaded by the runtime.

2. **Make the parent authoritative for launch controls.** Use an absolute pinned executable, literal fixed arguments, private cwd and controlled configuration; do not invoke package scripts, `bunx`, a shell-built command, or accept caller-supplied preload/loader/arguments. Construct the child environment from an allowlist. Do not inherit `NODE_OPTIONS`, `NODE_PATH`, `BUN_OPTIONS`, loader flags, package/cache search settings or arbitrary `PG*` settings. Provide required OS/TLS values deliberately. Set fresh private home/config paths in the child environment only; do not change the user's environment. Disable automatic env-file loading and installation. The existing author's Bun 1.3.12 probe establishes only its tested `--config=<path>` negative control; independently test the full launch profile on the actual pinned version before relying on it. Parent-recorded arguments/config/environment policy, rather than mutable child `process.execArgv`, are the evidence. Keep credential values out of argv, reports and journals; pass them through the reviewed private channel only after artifact validation.

3. **Bound drift honestly.** Execute solely from the fixed private artifact, never from the active worktree. Verify its manifest immediately before spawn and retain the package exclusively through worker exit. Treat any modification as a failed execution boundary and reconcile an entered migration. This is a trusted-host artifact discipline, not an adversarial filesystem proof; post-run hashing is a diagnostic only. If stronger mechanical reduction is cheap, build a single reviewed worker bundle with embedded SQL and ship no runtime-resolved application files. But do not make bundling a new open-ended prerequisite: the current dedicated adapter uses `createRequire(new URL(...package.json, import.meta.url))('pg')`, and the source lock uses module-relative SQL paths. A claimed standalone bundle needs deliberate changes and renewed tests for those paths, optional/native dependency loading and runtime external imports. A build graph must not be relabeled a runtime-observed graph.

4. **Version the contract rather than spoof the old one.** Introduce an execution-artifact launch profile containing the independently authenticated release head, source archive/dependency/runtime/supervisor/config digests, fixed entrypoint, launch-policy identifier and actual operator/reviewer identities. State `trustBoundary: trusted-operator-host` and the exact claim: reviewed artifact launched with controlled inputs. Omit `moduleGraphComplete`, `runtime-loader-observed-v1` and hostile-host immutability assertions. Extract/reuse the current source lock's synchronous private manifest snapshots, exact normalized SQL digest checks, at-most-once migration invocation and nonexposed private SQL. Bind those to the new artifact identity through the real supervisor, not an arbitrary caller callback that returns true. Keep the old v2 factory fail-closed for old callers or retire it explicitly. Update transactional publication/source binding terminology and journal profile so `sourceClosureSha256` cannot silently change meaning. SQL must be read once, compared to the reviewed manifest and retained privately before entering the database transaction; backing-file changes must not change executed SQL.

5. **Enforce one worker, one adapter, one transaction.** The supervisor reserves a fresh external durable journal and launches a fresh child dedicated to this attempt. A fixed entrypoint constructs exactly one dedicated adapter and performs the one transaction; there is no general dispatch, second adapter, retry, watch mode or reusable worker. The bounded adapter review requires this process-level constraint because a second instance has an unresolved intermittent hang. On success/error the child exits after bounded teardown. The parent holds an outer deadline, terminates only its own exact child if necessary, and preserves an uncertain/no-retry record. No child exit code or kill alone establishes rollback. Reconciliation uses another newly supervised process after authenticated original-server-transaction resolution.

6. **Retain database and recovery protections.** Authenticate the exact primary/TLS target. Acquire the native sequence fence and deterministic legacy table locks in the one physical transaction; derive the schema-22 baseline under lock; compare to the accepted restored archive; execute only pinned migration 23; compare legacy rows, numeric/JSON representation, histories, sequences, ACL/policy/catalog scope and the explicitly permitted delta before COMMIT; record the migration marker atomically. Preserve hard server transaction timeout and adapter ownership. A stale archive fingerprint refuses rather than adopting the live difference silently; refresh backup/rehearsal or independently account for authorized differences before a new attempt. The fence cannot make own-session `nextval`/`setval` rollback-safe: the reviewed migration must avoid those writes. Maintenance stop coordinates old-app availability, not database preservation. Postcommit restoration/downgrade is never automatic because it may replace data and needs the board's applicable decision.

## Independent acceptance tests for the replacement

- Authenticate a real published synthetic candidate through the supervisor; refuse wrong head/checks, changed archive, changed installed dependency, wrong executable/config, unresolved dependency, external junction and stale/tampered evidence **before any database connection**. Test the exact supervisor entry, not only injected verifier stubs.
- Challenge ambient local/parent/home config, `.env`, preload aliases, `NODE_OPTIONS`/`BUN_OPTIONS`, altered PATH, package scripts and malformed request arguments with harmless markers. No marker may execute and no unexpected file/code fetch may occur. Test the pinned installed runtime; current online documentation is not evidence for every Bun 1.3.12 behavior.
- Modify the active working checkout while the private worker is running: it must have no effect. Change reviewed SQL on disk after pinning: executed SQL must remain the accepted private bytes. A malicious rewrite of the private artifact is outside the trusted-host premise; do not count a before/after hash test as defeating the retained reversible-tamper attack.
- Verify one child/adapter/transaction/backend identity; refuse second construction in the fixed workflow, repeated journals and attempted retry. Force nonsettling callbacks, server deadline, loss during COMMIT, process kill and journal failure. Keep uncertainty, never restart migration automatically, and demonstrate separate-process reconciliation against the correct resolved transaction/primary.
- Execute the real artifact against a fresh restored native PostgreSQL 17 clone with concurrent normal table and sequence writers. Independently compare the full before/after preservation surface, exact allowed delta, rollback on deliberate mismatch, released locks and no residual child/session. Include final catalog/security drift and currentness refusal. Do not substitute PGlite or synthetic attestation objects for this composed review.
- Bind reviewer disposition to exact supervisor, artifact, source-lock replacement, dependency/config/runtime and runner hashes. Then publish/revalidate the integrated release before the one-time hosted stop/upgrade. Retain independent actual-result review, target observations, recovery limits and the required hosted board demonstration.
