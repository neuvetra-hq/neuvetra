# Collection evidence orphan recovery (synthetic staging)

This is the operator path for a collection upload that reached private Storage but did not finish database registration. Application users cannot read a pending original, delete it, or mark it clean. Keep that boundary in place. Migration `0027_collection.sql` must first be applied through the separately reviewed migration process; this runbook does not apply it.

Use the upload reference shown in the collection screen. Work on **one** recovery row and **one** exact object key at a time. Use the approved operator PostgreSQL credential and the provider's Storage administration interface; never paste either credential into a note, ticket, command argument or log. Deleting a hosted object requires the board's separate hosted-data deletion authorization. Do not use this procedure for real customer data without a new review.

1. Read the pending `neuvetra.collection_evidence_orphan_recovery` row by company ID and upload ID. The route's best-effort recovery marker can itself fail during a database outage. If there is no row, read the exact committed `collection_evidence_upload_intents` row and confirm that its Storage object exists while no upload receipt or evidence object is attached. An operator, with no application-actor impersonation, calls `neuvetra.reconcile_collection_evidence_orphan(company_id, upload_id)` to create or replay the pending recovery row. That operator-only function refuses a missing object, wrong company or attached upload. If both the recovery row and object are absent, note the abandoned intent in the private operator receipt only; no database recovery function records that state, and the user can reload and start a new upload. For an actual orphan, join the intent and recovery rows and record the exact recovery ID, private bucket, object key, expected SHA-256, byte length, media type, creator and reason in a private receipt. Confirm the key is exactly `<company-uuid>/original/<upload-uuid>` in `neuvetra-private-company-evidence`. Stop if the identifiers or intended tenant differ.
2. Check `collection_evidence_objects` and `collection_evidence_uploads` for that company/key/upload. If the key is attached to an evidence object, **do not delete it**; investigate the registration and quarantine history instead. A pending recovery row alone is not permission to remove referenced evidence.
3. With separate board authorization for hosted deletion, inspect that **exact** object through the provider's Storage administrator interface or an isolated scanner. If it exists, compare its size and SHA-256 to the intent without previewing or executing it. If the bytes disagree, preserve them in quarantine and escalate the integrity discrepancy; do not record recovery. Delete only the exact object from the private bucket through the Storage API/admin interface, never by deleting a `storage.objects` database row directly or by prefix/bulk deletion. Verify both the Storage API and `storage.objects` no longer report that exact object. If no object ever existed, record that observation and do not issue a delete.
4. In one operator transaction, re-read the same pending recovery row and absence of the exact Storage object, then call `neuvetra.resolve_collection_evidence_orphan(company_id, recovery_id, 'recovered', note)`. The function is not granted to application roles and refuses `recovered` while the object still appears in `storage.objects`. Commit and read back its `status`, `recovered_at` and note. Keep a receipt with timestamps and object metadata, not secret values or original bytes.
5. Tell the synthetic user the attempt was reconciled. They should reload the collection page before selecting the file again; the new attempt gets a new upload ID. The original failed intent and recovery receipt stay as history. Any successfully registered replacement remains `pending` until a **separate trusted scan** appends a clean/rejected/error event through the operator-only quarantine function. Never infer `clean` from a successful upload or from orphan cleanup.

If the provider deletion response is ambiguous, stop and re-observe the exact object through both interfaces; do not repeat deletion or mark recovery based only on an attempted request. If the database receipt is ambiguous, read the recovery row before considering another call. A second call must not be treated as a fresh operation. The collection UI's reference is an identifier for reconciliation, not proof that bytes were stored.
