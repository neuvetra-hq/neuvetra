# Agent improvement cycle

Policy version: 2026-09-14.1. Owner: CEO coordinator. Independent evaluator: Head of QA.

This is an implemented local operating workflow and evidence checker, not a persistent worker, scheduler, automatic model router, or proof of improved performance. It applies to **new assignments**. Work already dispatched, including the concurrent product milestone, keeps its agreed scope and settings. Do not interrupt, restart, change settings for, or add acceptance gates to that work retroactively.

## Start a new assignment

For new bounded build assignments, use the [local workflow controller pilot](workflow/README.md) to record dependencies, attempt reservations and targeted review returns. This supplements the role records below; tickets are not running agents, and the controller does not replace independent judgment or existing production gates. Do not migrate already-started work or consumed authorizations into a fresh journal.

1. Read the latest board instruction and the leading current section of `operations/next-session.md`; distinguish dated closure from currently observed activity. The product coordinator owns the main ledger, board report and continuation file. Historical entries are not current instructions. Consult this directory's [status](status.json) separately for the agent-improvement workstream.
2. Read the [operating model](../agents/README.md), the selected role prompt, and only the evidence needed for this task. Supply a compact handoff with objective, criteria, owned paths, dependencies, exact versions, known lessons and exclusions. Prefer a fresh context for independent review. Full-history forks are justified only when the whole history is needed; they inherit compute settings under the current tool contract.
3. Use the [role registry](roles.json) and [compute policy](compute-policy.md). `python tools/agent_ops.py dispatch software-engineering --task-id EXAMPLE --executor /root/example` prints requested settings and prompt hash. It does not spawn a worker. Copy the requested model/effort into a supported fresh-context dispatch, together with the complete bounded assignment. Verify the actual setting when observable; otherwise retain `null` and label it unknown. Do not silently describe requested settings as applied settings.
4. Create a record from [run-template.json](run-template.json) under `runs/` using a unique task ID. One writer owns each record. Record parent outcome, role, actual executor, requested/observed compute, prompt hash, artifacts and criterion-to-evidence map. Preserve original first-review results; later repair must not rewrite failure as first-pass success. Never add credentials, raw conversations, customer data or evaluator answers.
5. Choose applicable [lessons](lessons.json) before implementation. The engineer exercises actual public boundaries; QA independently checks the exact delivered version. A test count is not evidence that a specific acceptance criterion was exercised. A changed artifact invalidates the old verdict for that artifact until targeted re-review.

If a fresh dispatch is rejected by a runtime limit, record the rejection and actual fallback executor. Reuse an existing independent reviewer only after checking prior authorship and refreshing the bounded role brief. Keep inherited model/effort unknown unless observed; a rejected model request is not an applied setting. Preserve the substantive review gates and report the routing exception at closure.

## Close and learn

The coordinator runs `python tools/agent_ops.py validate` and `python tools/agent_ops.py summarize`. The checker verifies record structure, local evidence paths, hashes and declared completion gates. It cannot establish that evidence is true, a reviewer is genuinely independent, a cited passage supports a claim, or a role is competent. Independent QA makes those judgments. The scoped GitHub workflow runs these checks on future changes; it does not run agents or grade their substantive work.

Before closing a run, freeze its reviewed outputs into an immutable artifact under `snapshots/` and bind that artifact in both `artifacts` and `review.reviewed_artifacts`. The bootstrap uses one JSON bundle with original path, SHA-256 and UTF-8 text for every reviewed text file; QA verifies each entry against the candidate. Keep the original source map in `source_artifacts`. Do not include the bundle itself, mutable run/status metadata or the review being written inside its own bundle. Binary outputs can be separate immutable artifacts. Later changes get a new snapshot and review, so historic acceptance survives without falsely approving the new live code. Never overwrite an accepted snapshot. Snapshot text is historical evidence, not a replacement for current instructions. The checker validates the bound file bytes; it does not interpret bundle contents or prove that current source files still equal a historical snapshot.

At each accepted assignment, record first review, material rework, repeated findings, defects found after acceptance and actual resource observations. Unknown is `null`, never zero. A lack of later observation is not evidence of zero escaped defects. Record elapsed time separately from active work and waiting. Token counts are not dollar costs; cached input and reasoning tokens are subsets where the provider reports them, not extra quantities to add again. Cost requires an actual billing basis. Summaries retain known/unknown denominators and are not a ranking across unlike tasks.

Choose at most one or two consequential lessons per assignment. Link the original finding, assign an owner, change the relevant shared check or role instruction, and have an independent evaluator try a new variant. A lesson starts `adopted_pending_effectiveness`; move to demonstrated effectiveness only with a named later result. Prefer executable shared controls over adding repeated prose to every prompt. If an experiment increases rework or misses a material defect, revert the scoped change and retain the result.

The initial pilot covers the **next three eligible assignments begun after adoption**, not three historical tasks and not the already-running milestone. Bootstrap records for OPS-AGENT-02 are excluded from the pilot denominator. At the third closure, CEO compares coverage, rework, recurrence and observed resources with the stated task mix; QA challenges the interpretation. Three tasks give an initial signal, not a statistically reliable model ranking. Until then, effectiveness and savings remain unmeasured. This closure trigger is an instruction for future coordinators, not a background job.

## Add a role

Use [new-role-template.md](new-role-template.md). Define one accountable scope, sponsor, exclusions, evidence sources and independent reviewer. Add its prompt and a registry entry with supported default/critical settings; add a public benchmark brief to [benchmarks.md](benchmarks.md). The evaluator creates fresh cases and keeps scored expectations outside the candidate context. A role can be registered without claiming competence.

Onboarding proceeds by topic: `defined` -> `source_reviewed` -> `benchmarked` -> `supervised_assignment_accepted`; human validation remains separate where needed. Record dates and evidence at each transition. A reading list does not establish source review, and one benchmark does not establish general expertise. Never promote a role because its prompt calls it an expert.
