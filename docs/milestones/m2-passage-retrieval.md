# M2: correct the retrieval design

The board's second unsupported question prompted a root-cause review instead of another question-specific patch. This increment replaces the private prototype's answer path with a separately reviewed passage experiment. It does not advance the calculation milestone or deploy a public service.

**Current disposition: investigation complete; dynamic-answer release gate failed.** The final profile experiment passed software checks but produced only two independently clean complete answers out of eight questions. The local answering process is stopped; no new approved browser demonstration was performed. The [independent report](../research/scope2-passages-qa.md) retains all failures, and the [next reliability proposal](../research/scope2-answer-reliability-next.md) separates correctable refusals from missed defects. The code remains an opt-in private experiment, not a released replacement.

## Observed defect

The exact question was: “How do you source regional grid average factors (e.g., eGRID in the US) versus supplier-specific emission factors?” On baseline `fc97c487df156bfd6e9a589d34bfe8c67fdfc2b4`, an injected offline spy confirmed `unsupported`, zero evidence loads and zero model calls. The lexical domain gate rejects the question before evidence access.

Removing that gate alone is insufficient. The approved runtime has five fixed statements, with 71 words of main text, and six citation anchors totaling 13 words. It hashes the original PDF but does not give the supporting paragraphs to the model. The model can select stored statement IDs only. The previous compound-question correction improved those statements and routes without resolving this design limit.

Independent QA also constructed cases where approved IDs satisfy the old validator while omitting part of the question. These are controlled counterexamples, not live model accuracy measurements. The [evidence assessment](../research/scope2-retrieval-root-cause-evidence.md) and [independent review](../research/scope2-retrieval-root-cause-qa.md) preserve the distinction between missing corpus coverage, retrieval failure and incomplete answers.

## Chosen implementation

Keep the original v2 engine, release and recorded runs intact. Build a separate opt-in local entry point under `apps/site-api/src/research-passages/`. The normal provider-disabled default remains. The experiment uses the same local browser contract, with an explicit answer mode so generated answers are not labeled as prewritten reviewed statements.

The evidence author prepares coherent EPA paragraphs by section, with original PDF and normalized extraction hashes, page offsets, paragraph hashes, review status, permitted use, applicability, exclusions and required neighboring passages. This covers reusable purchased-electricity concepts; it is not a list of answers authored for individual board questions. Copied third-party criteria and detailed eligibility determinations remain excluded pending their own review.

Each answered question has three bounded model stages:

1. Identify the material parts of the original question and select relevant passages by meaning from the entire small approved section catalog. The server fetches their actual text and required context. There is no domain-keyword whitelist or query-specific synonym rule.
2. Draft concise atomic claims grouped by each requested part, with bounded space for every group and passage IDs. The server resolves the full original paragraphs and retains reviewed mandatory qualifications; the model does not retype quotations. Missing, duplicate or substituted groups withhold the whole answer.
3. Use a separate fresh-context call to check the original question's decomposition independently, then challenge support and completeness for every part and claim against the full selected passages. Exact group and verdict bindings are server checked. Display only after validation and rechecking the release and original-source hashes.

Planning uses Sonnet 5 with thinking disabled and a 1,200-token output cap. The current comparison changes drafting to the same Opus 5 adaptive/high profile as verification, with an 8,192-token total output cap per stage, including reasoning. Each claim can draw support only from its own citations and their approved dependencies; other selected paragraphs may expose contradictions or omissions but cannot supply uncited support. The server's stage metadata records the actual planning, drafting and review profiles. The draft-profile change requires its own live evaluation.

Source authorization, action scope, reference integrity, output shape and numerical-execution limits remain server controls. Model agreement is fallible evidence, not proof of factual support or professional assurance. No generated draft streams to the browser. Unsupported coverage, source validation, answer validation, timeouts and exhausted budgets have distinct fixed diagnostic reasons; raw model rationale and credentials do not enter responses.

A separate output guard rejects unsupported numeric literals and recognized quantitative emissions, activity and factor expressions; contextual source years, Scope 2 labels and unit names can remain. This checks output provenance and quantity formats, not a list of allowed questions. It does not prove that every possible paraphrase or obfuscated quantity will be caught. QA demonstrated that a deliberately wrong verifier can approve a false conceptual claim with a real quotation; this residual risk prevents treating the experiment as assured professional advice.

The first passage live batch failed: six of eight questions were withheld, and one of the two displayed answers left its requested rationale implicit. Separate private diagnostic calls then confirmed correct source selection followed by 1,200-token truncation while copying quotations, duplicate quote entries permitted by the output schema but rejected by validation, and a purported exact quotation with an inserted ellipsis. These are observed contract failures, not an inference that every earlier withheld answer had the same cause. The compact correction removes repeated model quotation output, bounds both individual and total claim length, and asks for the requested relationship directly when supported. It preserves exact server-resolved paragraph text, IDs, dependency context and semantic review. Removing copied quotations loses an extractive navigation hint; exact copying never proved entailment. Historical runs are not rebound to the changed code.

The compact eight-case regression then produced six answers and two review refusals, but independent review rejected the known sourcing answer: it spent four claims on the grid side and substituted a generic market/certificate description for the supplier workflow. A global completeness verdict had accepted it. The next structural correction groups claims by requested part, limits monopolization of answer space and requires a separate verdict for each group. These checks establish that groups and verdicts exist and match; whether a claim actually answers its part remains a fallible semantic judgment. No citation count or group count is presented as proof of accuracy. The compact run's exact code files are retained in its [snapshot archive](../../evaluations/research-qa/snapshots/scope2-passages-compact-code.zip).

The facet regression still failed its live gate. Original stage traces showed two withheld drafts reusing claim IDs across groups; one also exceeded its group limit by one character. The server now assigns IDs in canonical facet order and drafting targets leave 25% headroom below unchanged hard bounds. An independent replay of the original sourcing draft passes structurally after removing obsolete ID fields; that is not a new model result or semantic pass. The original overlong draft still rejects.

Independent review also found a released answer that dropped a source condition, strengthened a recommendation into a requirement and relied on evidence absent from one claim's own citations. The AI critic accepted it. A separately recorded comparison replays identical exposed good/bad verifier packets with reasoning enabled on two models, preserving the baseline prompt and schema. Its purpose is to investigate a reviewer configuration, not estimate general accuracy. The original [facet implementation snapshot](../../evaluations/research-qa/snapshots/scope2-passages-facet-code.zip), failed outputs and actual first-attempt trace provenance remain preserved.

The [completed comparison](../research/scope2-verifier-comparison.md) found that Opus rejected the bad answer and accepted the good one, while still missing a separate claim's citation gap. Sonnet exhausted the comparison's 4,096-token cap on both cases without a final verdict. The next configuration increases verifier headroom and clarifies claim-local citation support; it is not the configuration tested by that two-packet diagnostic. Broader live results and independent semantic review remain required.

The subsequent eight-case run04 with the stronger verifier produced four independently complete, source-supported answers, one answer with a claim-local citation gap, and three withheld answers. The known sourcing question passed in that sample. Traces distinguish a likely false-negative reviewer decision on ancillary content, a correctly rejected timing overstatement, and a draft that still exceeded its group limit. The next experiment changes only the draft profile as a bundle (model, thinking and token cap); prompts, schemas, source release, hard bounds and questions remain fixed. This avoids adding question rules or silently dropping rejected claims. Run04's [exact code snapshot](../../evaluations/research-qa/snapshots/scope2-passages-reasoning-code.zip) is retained.

That draft-profile comparison, run05, did not improve the observed gate: three answers were released, two were independently clean, and five were withheld. The deficient released answer omitted a necessary quality prerequisite. Several withheld drafts added unnecessary stronger or causal language; not every refusal can confidently be called correct or incorrect. The [run05 snapshot](../../evaluations/research-qa/snapshots/scope2-passages-drafting-code.zip) preserves the final implementation. This is not a broad ranking of models, and the earlier successful sourcing sample is not rebound to the later code. The two final fresh probes and the old H-S03 regression were not rerun because the preceding gate failed.

For this small corpus, semantic selection from all reviewed catalog cards avoids a separate embedding service and its recall/version dependencies. A larger corpus will need a measured retrieval comparison. Adding a vector database alone would not repair missing paragraph content or incomplete-answer validation.

## Acceptance and evaluation

QA freezes a hidden question set across source-defined subject families before implementation is frozen. Questions cover paraphrases, combined intents, sourcing versus actual selection, missing context, unsupported operations and valid citations attached to insufficient claims. The engineer receives families, not the hidden prompts. Source approval, offline software tests, hidden retrieval/answer checks and real model behavior are separate gates.

The first three passage batches each reserved at most 30 attempted stages at $0.06 per stage ($1.80). The reasoning configurations use separately recorded 30-stage batches at $0.50 per stage ($15). These are coordinator-selected experimental envelopes, not board-imposed or provider account limits, and not measured billing. Earlier attempts and unused allowances remain recorded under their original batches. Failed and uncertain calls consume reservations; no automatic retries. All restarts must carry the current batch's remaining allowance.

Plan at most eight live HTTP questions (up to 24 stages), then one browser demonstration (up to three stages), leaving any remainder for review. Preserve failures and exact code/source/input bindings. Do not tune one hidden sentence at a time or describe controlled mocks as live results. A failed release gate remains visible and prevents promotion.

Final source approval, actual execution, limitations and the next board demonstration will be recorded in `docs/research/scope2-passages-qa.md` and the task ledger. Until that record exists, this document describes the approved implementation scope, not a working replacement or a passed evaluation.

## Reproduce the private experiment

Use Bun 1.3.12 and the existing workspace lockfile. From `apps/site-api`, `bun run start:research-passages` starts the separate local entry point on `127.0.0.1:3012`; it does not load the historical marketing backend. Stop the other local research process before using the same port. The frontend remains at `http://localhost:5174`, with its existing local proxy.

Set `RESEARCH_PASSAGES_RELEASE_PATH` to the approved `data/research/releases/scope2-passages.v1.json` and `RESEARCH_PASSAGES_RELEASE_SHA256` to the independently approved pin in the source/QA report. `RESEARCH_SOURCE_ROOTS` must explicitly include both the original PDF directory and the normalized-page extraction directory. The [source handoff](../research/scope2-passages-evidence.md) explains how to reproduce the normalized pages with `tools/research/extract_scope2_passages.py`; its output and original PDF stay in controlled local source storage.

The server-only provider/origin variable names from the [original pilot](m2-answer-demo.md) remain applicable. `RESEARCH_PROVIDER=anthropic` explicitly enables the configured adapter; the default is disabled. `RESEARCH_MODEL=claude-sonnet-5` and `RESEARCH_MAX_OUTPUT_TOKENS=1200` configure the planner only; drafting and verification have fixed Opus 5 profiles with 8,192-token caps. Set the bounded remaining `RESEARCH_MAX_CALLS`, `RESEARCH_CALL_RESERVATION_USD=0.50` and a corresponding `RESEARCH_MAX_SPEND_USD` (at most $15 for 30 stages). These current reservations cover the larger reasoning configuration; the earlier $0.06 batches remain historical records and must not be reused silently. Each answer can consume three stages. The service requires allowance for a complete answer before planning, allows one whole pipeline at a time, and has a 150-second overall deadline inside the browser's 155-second limit. Provider calls have a 90-second limit and the HTTP listener allows 160 seconds of idle time. Cancellation prevents later stages; failed/uncertain calls keep reservations.

After independent approval and a frozen implementation, run the selected live fixtures explicitly:

```sh
python tools/research/run_passage_eval.py --run-live --output evaluations/research-qa/runs/UNIQUE_PASSAGE_RUN.json
```

The runner checks response structure, exact source text/metadata, dependency references, qualifications, artifact pins and call counters. It records `mechanical_checks_passed` separately from `semantic_review`, which remains pending until independent review of the actual answers. It does not run in CI. A run artifact is never overwritten, and a release or code change invalidates the earlier binding rather than silently rebinding it.
