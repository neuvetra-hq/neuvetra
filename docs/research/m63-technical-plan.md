## Trust and migration contract

1. Validate the supplied bearer token against the configured Supabase project; fail closed on invalid, expired or unavailable validation. Authorize an active M63 invitation and database membership on each request, including downloads. Never accept a user/role from headers or body as identity. An existing JWT does not override a revoked M63 invitation. The existing `create_company_workspace` function checks only nonnull `auth.uid()`: new SQL access policy must also prevent a non-invited Auth subject from using direct database/Data API entry points to bypass the invitation gate. Keep the workflow schema unexposed to PostgREST where possible, with no general authenticated execute/write grants that reopen the path.
2. A dedicated runtime database login is non-owner, `NOSUPERUSER`, `NOBYPASSRLS`, with no migration, schema-create, role-management or unrestricted membership-writing authority. Do not inherit the general `authenticated` role merely to make existing policies work. Add explicit scoped runtime policies/SELECT/function grants instead. Keep credentials server-only with verified TLS/hostname and bounded connection/statement/lock timeouts.
3. Every operation sets the verified subject in a transaction-local claim context on the same reserved connection. Commit/rollback releases that context; pooled connections must not retain another request's subject. Client-supplied SQL or arbitrary claim-setting endpoints are forbidden. Test both success and exception cleanup.
4. Replace the two local execution modes with explicitly scoped hosted transactions. Read paths remain under RLS. Trusted domain writes call individually granted security-definer functions that independently check membership/manager authority, exact predecessor state, immutable history and separation of duties. Their fixed search paths and owner privileges require review; forced RLS alone does not protect against a superuser/function owner that bypasses it. M63 runtime cannot directly insert fabricated calculations, report bytes or decisions into underlying tables.
5. Apply original migrations in order through a controlled migrator, plus an additive M63 access/role migration. The host already owns `auth.users`, `auth.uid()` and standard roles; do not recreate them. Record migration names/checksums/version and fail on an unknown or partially applied baseline. Keep migration and role provisioning transactional where supported. No app-start schema writes.
6. Prove PostgreSQL-driver compatibility for placeholders, multi-statement execution, transaction affinity, JSON/JSONB, `bytea`, UUID, timestamps and numeric text. Preserve decimals as strings and canonical JSON/timestamps, with reordered-equivalent input tests. Real database constraint/idempotency races must converge across separate connections and restarted processes; an in-memory promise map is only an optimization.
7. Freeze a staging runtime asset manifest: linked calculation Python and imported method, database modules/migrations, fixed bill PDF, register JSON/manifest, all transitively referenced authority/replay assets and staged web build. Verify hashes in the actual image. Do not copy the full repository, memory archive or output directory.

## Monitoring, recovery and release gates

Expose a minimal unauthenticated liveness response and a readiness check that verifies the expected schema version, a bounded database operation and required asset hashes. Return finite unavailable responses; no environment values or raw driver errors. Emit structured request ID, route class, status, latency and sanitized error category. Keep tokens, emails, notes, artifact contents and arbitrary request bodies out of logs. Configure and demonstrate the actual host's failure/health alerts; a runbook alone is not monitoring. One replica is acceptable for this bounded rehearsal, with bounded request/rate limits and database timeouts recorded as a limitation.

Before migration/deployment, capture an authorized baseline and restore target. For the small synthetic namespace, an explicit scoped logical backup must include schema, access configuration/membership references and all byte objects; ensure it cannot sweep customer schemas or credential-bearing auth tables. Restore original Auth subject UUIDs in the disposable target using an approved identity recreation path: remapping UUIDs rewrites audit lineage and cannot count as an exact-record restore. Keep backup files outside Git with restricted access and a manifest/hash. Provider backup retention/PITR availability remains unknown until verified and is not a substitute for an actual restoration drill.

Restore that backup into an isolated disposable database; replay inventory, pack, report and second-manager decision with exact hashes and run access probes again. Record actual backup age, restoration duration and any lost writes. Proposed bounded rehearsal targets are zero loss relative to a quiesced snapshot and recovery within one operator session; CPO/coordinator should define measured acceptance rather than imply a production SLA.

Rollback selects the previous known image/commit and compatible schema version, freezes new writes, and preserves accepted history. Additive migrations should support the prior image; do not roll back by dropping accepted records. Rehearse a failed candidate leaving the prior deployment healthy and a current candidate rollback with database continuity. Record image/build/deployment IDs, health result and exact restored artifact hashes. Public DNS cutover is not needed.

## Independent implementation partitions

The initial adapter interface should be small and structural: `WorkspaceSql.query<T>(sql, params?)` resolves `{ rows: T[] }`, and `WorkspaceSql.exec(sql)` resolves void; `WorkspaceConnection.transaction(callback)` supplies one such transaction on one reserved connection and `close()` releases resources. Normalize driver results at this boundary. A shared database class owns domain behavior; the existing development factory installs fake Auth/migrations on PGlite, while a hosted factory receives an already migrated connection and selects the scoped runtime transaction behavior. The hosted factory must not expose the local trusted bootstrap that directly inserts arbitrary memberships. A separate reviewed provisioner establishes approved Auth-subject/role relationships, and an idempotent staged workspace bootstrap creates only the configured synthetic owner workspace and approved memberships atomically.

The shared API composition takes that database behavior plus authentication/access dependencies, allowed origin and a bounded calculator runner. The development server supplies the existing token map/local factory; the new staging server supplies real `getUser` validation, active invitation lookup and hosted factory. Add a server-authenticated workspace discovery/access endpoint returning the caller's workspace ID and role; browser storage cannot be its authority. Keep all M54–M61 route response and snapshot contracts unchanged unless a separately reviewed M63 profile explicitly changes presentation metadata.
