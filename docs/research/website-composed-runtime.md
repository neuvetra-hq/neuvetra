## Request and display contract

The browser submits only a question. A planning model proposes a bounded decomposition using exact fragments of that question and known unit IDs. Each candidate unit now includes its server-computed companion closure and title-and-text character cost. The server validates every selected ID and facet before measuring the complete deduplicated closure, adds all mandatory companions and orders units by the reviewed catalog. Unknown IDs, extra fields or cycles cause withholding. The final composition remains limited to eight units and 4,000 title-and-text characters; content is never shortened to fit.

A separate model assesses the original question and the complete proposed composition for coverage, relevance, scope, context and premise handling. Its output is an internal assessment, not answer prose. Both stages must preserve an appropriate whole-question boundary: related conceptual material cannot substitute for a requested company-specific causal diagnosis, eligibility determination or other excluded action, and a mixed request cannot be presented as answered by its covered portion alone.

A valid request normally uses **two stages**, selection and review. A fully valid known-ID selection whose measured closure is oversized may receive one complete replacement selection and then a fresh review, for **three stages**. A valid semantic review requesting revision may instead receive one complete replacement selection and a new review, for **four stages**. These paths share one correction allowance; they cannot be combined. Size diagnostics provide measured closure and limits, never trimmed text or permission to omit a requested facet. Malformed outputs, unknown IDs, truncation, network errors and a failed correction do not receive hidden retries. Internal review explanations have a bounded 2,000-character limit and are never rendered as answer content.

Accepted responses use `cloud_reviewed_composition` and `reviewed_verbatim` provenance. The server renders exact approved unit text. The [frontend decoder](../../apps/site-web/src/lib/research-api.ts) independently checks catalog identity, exact text, title, type, citation IDs, companion presence, order and size. The [answer panel](../../apps/site-web/src/components/ResearchAnswerPanel.tsx) visibly distinguishes **Reviewed source summary** from **Reviewed interpretation** and provides original-source disclosures. Neither a plan, review explanation nor model-written connective sentence is displayed as a factual answer.

## Private operation and demonstration

1. Use the explicit private operator launcher with the existing approved reader and target configuration. Do not automatically load an environment export. The answering process receives ordinary-reader access, not a Supabase administrator credential. The launcher must persist new sessions securely before they are adopted; failed refresh or persistence requires investigation rather than a hidden password fallback.
2. Start the candidate on loopback port **3016**. Startup verifies reader/cloud integrity and the pinned catalog before opening the endpoint. Confirm `/research/status` reports ready. Readiness requires at least four remaining stages; it does not prove semantic answer quality.
3. Complete the [independent acceptance contract](website-composed-acceptance.md): the unchanged eighteen questions, two fresh probes, exact-output and failure-boundary checks. Retain every attempt, including errors and permitted corrections. Do not reuse a failed run as successful evidence.
4. After the quality gate, run the same approved candidate on loopback port **3012**. The website at [localhost:5174](http://localhost:5174/) already proxies `/research-api` to that port. Demonstrate both original questions through the actual answer panel, inspect source disclosures, then check boundary/error transitions, keyboard use and the narrow viewport. A direct API result or saved report does not complete this browser gate.

Only the configured localhost origins are accepted; responses are not cached. The service allows one active answer, applies a bounded deadline and honors cancellation. The panel preserves a typed question while offline, disables submission until ready and offers a connection recheck. Loopback and a private research reader are not customer authentication or a production deployment.
