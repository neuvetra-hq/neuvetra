# M71 saved synthetic corporate coverage contract

Implementation handoff, M71-BACKEND. Requested Astra/high; observed settings unknown. Source of truth for browser-safe types and seed: `packages/neuvetra-database/src/m71-contract.ts`. Canonical snapshots are the bounded implementation of M70's proposed normalized tables. Version identity versions every contained record; stable record IDs never disappear. General evidence uploads, released methods, calculations and legal determination remain outside this increment.

## HTTP and browser integration

All paths begin `/workspace/{companyId}/corporate-inventories` inside the existing `/workspace-api` staging prefix. Existing bearer/origin rules apply.

- GET collection returns `M71Register` (empty versions/head/inventory null before creation).
- POST collection accepts `M71SaveInput` with null expected version/hash and correction reason; returns the exact created `M71Version`.
- GET `/{inventoryId}` returns `M71Register`.
- GET `/{inventoryId}/versions/{versionId}` returns exact `M71Version`.
- POST `/{inventoryId}/versions` accepts `M71SaveInput` with current expected version/hash and nonempty correction reason; returns exact created version, including idempotent replay of an older request.
- POST `/{inventoryId}/reviews` accepts `M71ReviewInput`; returns exact `M71Review`.
- GET `/{inventoryId}/versions/{versionId}/coverage-export` downloads canonical UTF-8 JSON for that version **with review null**, frozen at save. Later reviews are returned separately by version/register reads; they cannot alter original export bytes.

All mutation inputs reject additional fields and duplicate JSON keys. Labels/reasons normalize trimmed Unicode NFC; text limits count Unicode characters. Set arrays sort by stable ID; evidence purposes and missing facts sort by Unicode code point, matching PostgreSQL C collation. API returns 422 for invalid/no-op, 409 for stale head/key conflict/review conflict, 403 for members attempting writes, 404 for inaccessible tenant/object, and bounded 503 for failed integrity. Reads have no-store. Only current owner/admin managers write; only a manager absent from the accumulated contributor set can review. Label-only, screening-reason-only, evidence-only and correction-reason-only successors are meaningful; no-op compares both the complete normalized snapshot and correction reason.

The bounded synthetic profile permits 40 versions, 50,000 UTF-8 bytes per normalized snapshot and 3,800,000 total frozen export bytes. The remaining 200,000 bytes of the 4 MB response budget cover the limited review records and envelope. A capacity refusal occurs before history/head mutation and leaves existing read/export access intact. API 422 codes distinguish `history_limit` and `history_bytes_limit`. These are demonstration bounds; production history pagination and customer retention policies remain future work.

Per current board direction, the seed includes only California parent/distribution operations, two facilities/electricity sources, the expected control relationship, full effective intervals, boundary decisions, all 25 required group screenings and two source detail rows. California-first reporting does not authorize omitting operations elsewhere: discoveries remain in the corporate boundary with visible geography/method gaps. Recording them does not launch another jurisdiction's regulatory product. Managers can edit typed snapshot fields and add discoveries; supported profile gaps become findings. Existing entity/relationship/facility/source/coverage/requirement IDs cannot be dropped or repurposed. Entity decision intervals must cover every active interval without overlap. Missing data is null; explicit zero requires quantity, unit, reason and supporting evidence. All methods stay not-assessed/unsupported/candidate; no released method value is accepted.

Synthetic evidence references may only resolve to the pinned `M71_ARTIFACT` ID/hash/locator for 2025. Linking proves the fixture reference, not evidence sufficiency. Exclusion/non-applicability requires a rationale and supporting reference at submission; even accepted assertions remain open, unverified findings. Proposed estimates additionally require a method candidate, assumptions, input references and uncertainty. Requirement rows permit only unknown/conflicting applicability and carry missing facts. Derived completeness is always incomplete, release eligibility false, emissions null and assurance none.

## Persistence and recovery

Additive migration 0015 follows observed schema 14. Its reviewed candidate SHA-256 is `2766561decde3ea64bf56f30b1b67a9144318e14b6efecaa71e05e8ae6351d19`. Immutable version/review/request/audit records, mutable tenant head, forced RLS and runtime SELECT/approved function execution only. Writers lock admission then membership then company/head; recheck permission; resolve prior idempotency outcome; compare expected head; retain accumulated contributors and immutable predecessor; atomically save audit/request/head. No startup migration or rewrite of prior receipts. Deployment/backup/restore is coordinator-owned; rollback after writes means restore a verified schema-14 backup and matching prior application, preserving an export of M71 records first. Do not down-migrate destructively in place.

The version content hash covers the normalized snapshot; the version hash additionally binds tenant/inventory/version/predecessor, creator, captured time, contributors and correction reason. SQL freezes canonical export text at save. Readback recomputes the bundled synthetic artifact text hash against its pin and independently checks normalized snapshot semantics, derived findings against retained export bytes, native columns, predecessor/contributor lineage, hashes, exactly one matching audit and exactly one reconstructed operation fingerprint per saved version/review. Idempotent save responses retain review null, so later review does not change the original response/export. Current exact-version reads expose later review separately.
