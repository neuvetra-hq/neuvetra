## Bounded diagnostic addon

`tools/staging/m76-hosted-baseline-diagnostic.ts` invokes the unchanged recovery helper in baseline mode through its supported dependencies, using an isolated in-memory helper journal. It refuses every other input mode before transport. Its observer refuses **all application methods except GET before calling fetch**, even if the frozen helper attempted an ordinary successor. Auth POSTs admit only the fixed project's password-token and local-session logout endpoints. Other origins, tenants, query variants and admin paths are refused.

Both failed journal byte hashes, the failed recovery terminal hash/two-event status, and exact frozen helper/recipe hashes are mandatory preconditions. The addon creates an exclusive private `.superpowers/m76-baseline-diagnostic-<timestamp>.jsonl`. It never appends to, truncates, renames or rewrites either failed journal. It checks their unchanged bytes at completion. The trace is serialized and flushed; trace failure refuses further diagnostic work, while logout transport remains allowed so its own sessions can close.

Each request records a sanitized route with UUIDs replaced, method, call index, response status, elapsed time through full body receipt, body byte count/hash and a derived no-store boolean. Auth records omit body/hash/header observations. Failures record only `aborted_or_timeout` or `transport_or_body_bound`; no error strings, tokens, passwords, request bodies, raw response text or headers are logged.

Successful register GETs additionally run the existing family decoder and record verification/duration. Grouped boolean comparisons identify the original corporate head/review/actors, equipment head/absent review/two expected blockers, two gas streams/one generator, each current stationary head/review, and retained original family versions. Historical downloads with original baseline observations additionally record exact byte-hash/length matches or canonical proof-hash matches. The unchanged helper still performs its own complete comparisons and download/client checks. A final isolated helper event records only status, generic stage, application POST count and session closure. A refusal following successful transport without a false grouped comparison remains an internal client/precondition refusal; the preceding exact call sequence narrows it but is not a fabricated diagnosis.

Root authorized a narrow `cached_diagnostic_only` legacy adapter: the real failed run already reached the authoritative stage after passing its old legacy phase. The addon supplies only the original retained legacy snapshot for that isolated dependency; it creates no legacy Auth sessions or writes. Readiness, all current family records and historical downloads remain actual GETs. The trace and summary explicitly label this cache. It is not fresh legacy or baseline acceptance evidence.

## Explicit separate continuation boundary

Root authorized a separate wrapper after the successful read-only diagnosis, subject to independent review before another official read. `tools/staging/m76-hosted-continuation.ts` uses the unchanged recovery helper and recipe through only their supported journal load/append and original-evidence dependencies. Actual execution substitutes neither fetch, Auth nor legacy transport. It requires a fresh full actual baseline before its exercise; the diagnostic cannot supply that baseline.

Every mode verifies the exact original failed exercise, the second failed baseline byte/head pins, two-event failed/zero-write/closed status with no intents, and the exact successful diagnostic bytes/source/completion observations. The frozen helper/recipe hashes and unchanged 21 operation keys remain mandatory. An exclusive flushed lock prevents simultaneous invocations. Its fresh baseline exclusively creates `.superpowers/m76-hosted-continuation.jsonl` with a hash-chained `continuation_provenance` event binding both failed attempts, diagnostic, wrapper/helper/recipe bytes and exact keys. The frozen helper extends that same new chain. Neither failed journal is replaced, reset, promoted or edited; a sidecar is unnecessary.

Later exercise/revisit modes require the exact same provenance and clean, closed, verified history before invoking the unchanged helper. Any failed or unresolved attempt, changed source/provenance, altered journal or uncertain write refuses continuation. A second baseline refuses an existing file, including provenance-only or failed files. The wrapper never deletes journals or retries application requests; it releases only its own lock. A new failure requires a separate audited board/root decision. Root separately controls the fresh baseline and subsequent 21-write exercise authorization, service restart and read-only revisit.
