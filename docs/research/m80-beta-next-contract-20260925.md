- `invitations`: UUID, company/admission binding, unique SHA256 digest of 32 cryptographically random bytes encoded as 64 lowercase hex characters, normalized recipient email, role (`owner` or `member`), issued/expiry timestamps, issuer decision reference; terminal state pending/redeemed/revoked, redeemed actor/time/request ID. - `requests`: actor/request UUID unique, token-digest input fingerprint and immutable successful receipt. Equal request plus equal input replays only while the exact resulting membership generation and admission remain active, even after the original token expires; a consumed invitation is expected for this receipt branch. Different input is 409; different request against a consumed token fails. This is transport retry, not second redemption.
- `audit`: append-only issue/redeem/revoke/admission-disable events with IDs, actor and time, no token/digest/email/body. Membership revocation changes active state and generation, preserving history. Operator revocation and admission disable are mandatory local control-plane functions, not tenant HTTP routes. No operator credential reaches the app process.

`POST /beta-api/invitations/redeem`: exact JSON `{ "token": "<64 lowercase hex>", "requestId": "<uuid>" }`, no extra/duplicate keys, maximum 2 KiB streamed body, JSON content type, exact allowed Origin, bounded Bearer token, validated identity. No email/company/role/actor/release fields accepted. The server hashes the token before parameterized SQL; neither raw token nor its digest enters logs/URLs/telemetry/errors. Return 201 for a first commit or 200 for the allowed identical retry: `{ profile, companyId, role, membershipGeneration, state: "access_admitted_setup_pending" }`. No email, invitation metadata or preexisting company facts returned before success.

`GET /beta-api/session`: authenticated list of only this actor's active admitted beta companies/roles/generations, with fixed synthetic labels. Empty access returns an empty list, not another tenant's existence. `GET /beta-api/workspaces/:companyId`: own active admitted workspace access summary; same generic 404 for nonexistent and unauthorized IDs. Every read rechecks both membership and admission; no positive authorization cache. Neither endpoint proxies legacy M80 data or returns numbers/releases.

## Transaction, identity and failure semantics

1. Validate every bearer via the configured Supabase `getUser` pattern; derive actor only from that response. Separate beta auth adapter requires nonempty email plus `email_confirmed_at`, never metadata or a request claim. Existing shared `AuthenticatedUser` behavior need not change. The native harness substitutes only the identity provider response; it must label this as mocked identity validation, not live Supabase verification.
2. In one database transaction, set transaction-local `request.jwt.claim.sub` from that trusted actor. Authoritative functions use `auth.uid()` directly, not the staging-gated `current_user_id()`. Pass the getUser-derived email as an internal adapter argument (never a request-body value); recheck that it equals `auth.users` current email, the invitation recipient and the confirmed identity inside the function, with row locking sufficient to serialize an email/confirmation change; the function reads only the needed identity columns, while the runtime receives no auth schema/table access. Refuse absent/unconfirmed/ambiguous matching identities. Normalize email identically on issue and redemption (trim outer whitespace, lowercase; reject malformed/non-ASCII for this bounded slice; no provider-specific dot/plus rewriting). A future broader email policy requires review. Auth project and DB project must match in future hosted composition.
3. Serialize per actor (transaction advisory lock) and lock the admission then invitation in a consistent order also used by issue/revoke. After authenticated database identity checks and those locks, **look up the existing actor/request success receipt first, before requiring a pending invitation or testing token expiry**. If a receipt exists, different token-digest input returns 409. Equal input returns the original immutable receipt only if the current verified identity still matches the bound recipient and the exact resulting membership generation and admission remain active and not tombstoned. Invitation state `redeemed` is expected in this branch. Original token expiry after a successful redemption does **not** block this authorized receipt recovery: the actor already has session access. Revoked membership, changed generation, disabled/tombstoned admission or identity mismatch denies recovery and cannot recreate access. No matching receipt proceeds to the new-request branch.
4. **New-request branch only:** match digest, current verified recipient, pending status, active exact admission and allowed role; require expiry strictly later than database time rechecked after acquiring locks. A consumed token with a different request ID returns generic 404. Insert exactly one membership, mark invitation consumed, append success receipt/audit and commit together. Unique constraints remain the final arbiter. No partial grant or consumed token survives rollback. If the response is lost after commit, the identical actor/request/input uses step3 to recover the original receipt; sign-in/session also recovers access without reissuing a token. Generic 404 `Invitation unavailable.` covers wrong email, missing/expired/revoked/consumed token on the new-request branch, or unauthorized receipt recovery. No diagnostic-specific disclosure. Invalid body 422, unauthenticated 401, forbidden origin 403, same-key/different-input 409, unavailable dependency 503, limits 429/413. Do not sleep or retry implicitly.
5. Concurrent revoke/redemption is serialized: revoke-first prevents grant; redeem-first followed by revoke removes effective access. Admission-disable also fences later requests. An already-running read linearizes before or after revocation according to its authorization lock; next request must deny. Authentication or database failures never yield fallback membership.
6. Server-wide admission limiting before expensive auth and per-actor redemption limiting after auth (initial 60/min globally, 5/min per actor, bounded buckets); do not trust forwarded IP headers. These are single-process rehearsal controls. Distributed/enforced production limits and exact proxy configuration are a hosted gate. Logs contain route category/status/request ID/duration only. No raw error objects or SQL parameter logging. API responses are no-store with staging-equivalent response security headers.

The issue operator uses only the exact local fixture manifest and synthetic `.invalid` identities, supplies company/recipient/role/expiry/decision reference, writes digest plus issue audit transactionally, and hands the raw token to the local harness in memory. Never stdout/files/Git; no email SDK or send operation. Installation, issuance and revocation require separate operator connection, never runtime connection. A fixture address suffix alone does not prove synthetic identity; the exact allowlist is authoritative.
