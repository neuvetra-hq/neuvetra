## Delivered contract

`packages/neuvetra-database/src/index.ts` now exports the shared `WorkspaceDatabase`, narrow `WorkspaceSql` (`query<T>` returns `rows`, `exec`) and `WorkspaceConnection` (`transaction`, `close`), retained `DevelopmentWorkspaceDatabase`, and `HostedWorkspaceDatabase`. Existing domain behavior moved intact to `workspace.ts`; PGlite imports dynamically only when the development factory is invoked. Hosted deployments use pinned `postgres` 3.4.9, added to this package manifest; root updated the lockfile.

The hosted factory accepts `{connectionString, expectedProjectRef, maxConnections?, reuseExistingProject?, tlsCaPem?}`. It accepts only matching Supabase direct/session-or-transaction-pooler host/user shapes, `/postgres`, a dedicated `neuvetra_runtime` username, no URL query overrides, and verified TLS. A bounded explicit CA may be supplied through `tlsCaPem` or `loadStagingDatabaseCa({caPem?,caFile?})`: exactly one source, at most 64 KiB/ten parsed CA certificates, no private keys or arbitrary TLS options. The operator reads optional `NEUVETRA_STAGING_DB_CA_PEM` or `NEUVETRA_STAGING_DB_CA_FILE`; the public repository CA at `tools/cloud/fixtures/supabase-prod-ca-2021.crt` passes validation. The driver retains `rejectUnauthorized:true` and derives TLS servername from the target hostname; explicit CA with `tls:false` is rejected. Root/CTO own packaging the public certificate and runtime setting. Connection setup is bounded, prepared statements disabled for transaction-pooler compatibility, transaction/statement/lock timeouts set, and driver notices suppressed. Pooler TLS proves verified client-to-pooler transport; a false backend `pg_stat_ssl` result must not be described as absent client TLS or as verified end-to-end database TLS.

`checkReadiness()` validates the exact nine canonical SQL checksums, target/profile, non-owner NOSUPERUSER/NOBYPASSRLS/NOINHERIT runtime role, no memberships/DDL/direct table mutation grants, and forced RLS. No hosted factory or HTTP startup applies migrations or creates users. It returns `{profile:'neuvetra.private-synthetic-staging.v1',schemaVersion:9}`; confirmed reuse of the known existing project additionally requires current legacy containment and returns `legacyContainmentVerified:true`.

`hasStagingAccess(userId)` and `findStagingWorkspaceForUser(userId)` support API access/session discovery; discovery returns `{workspace, role, evidenceId}`. Every hosted domain operation sets the verified UUID using transaction-local claims on a reserved connection and checks active invitation plus membership. Read and write modes use the same restricted login. Security-definer membership/manager helpers also require the active invitation and its approved company, so bypassing the API gate or retaining an old JWT cannot restore revoked access. SQL functions preserve existing method, hash, immutable history and second-manager controls.

Workspace creation returns the operator-provisioned manager workspace; hosted synthetic-member injection is refused. Runtime has no membership/workspace-creation, schema-creation or table-write grant. Only the individually enumerated domain functions are executable. Original bytes, inventory versions, pack/report bytes and immutable review history remain in PostgreSQL.

## Explicit operator sequence

The board subsequently approved reusing the existing project and confirmed existing records are test data. Physical project isolation is no longer asserted. The operator must first capture the authorized recovery snapshot and inspect `auditLegacyStagingExposure(db)` / `planLegacyStagingContainment(db)`. These are metadata-only; no rows or passwords are returned. The follow-up audit discovers **all application schemas** from PostgreSQL catalog metadata on every run, including the observed `public`, `frontdesk`, `site`, `neuvetra_research_dev`, `terrascope`, and the M63 `neuvetra` namespace. Unknown/new schema names are applications by default and block readiness pending an explicit reviewed profile update, even if they are currently empty or have no endpoint grants. The reviewed set is `public`, `frontdesk`, `site`, `terrascope`, `neuvetra_research_dev`, `neuvetra`, and `drizzle`; the last is explicitly present without endpoint schema privileges in root's reviewed `.superpowers/m63-live-containment-plan.json` metadata receipt. It checks effective anon/authenticated privileges (including PUBLIC and inherited grants), schema USAGE/CREATE, database CREATE, relation/column/sequence privileges, callable functions and app/global default ACLs. New application schemas or column-only grants therefore invalidate readiness instead of falling outside a static table list.

The returned containment SQL is reviewable, not automatically executed. Execute the reviewed statements atomically with the privileged operator after backup, then rerun the audit. It revokes PUBLIC/anon/authenticated access across every application schema, including table, explicit column, sequence and function grants, plus database/schema CREATE and relevant default ACLs, while preserving administrative/service role grants. Inherited access that survives these statements remains visible and keeps readiness false; the plan does not silently alter unrelated role memberships. This is explicitly authorized test-project containment, not an ordinary HTTP-start repair.

Root's atomic cloud rehearsal rolled back when `postgres` could not alter `supabase_admin` defaults (SQLSTATE 42501). The revised policy is explicit: **only defaults owned by `supabase_admin`, scoped to `public`, for tables/functions/sequences** may remain as `deferredProviderDefaultGrants`. They are never removed from the audit receipt. Every existing application table/column/sequence/function grant must still be absent, effective schema USAGE/CREATE and database CREATE must still be denied to both endpoint roles, and unreviewed schemas remain blocking. Restoring schema USAGE, creating an object with a new effective endpoint grant, inherited access, any global provider default, or another owner's/application namespace's default blocks readiness. Default ACL discovery includes recipients whose privileges endpoints inherit.

`planLegacyStagingContainment` returns these unexecutable default changes separately as `providerAdminStatements`, alongside the complete deferred grant inventory and named `supabase-admin-public-defaults-behind-denied-schema-v1` policy. Normal statements never silently skip an unexplained permission error; the operator still executes its reviewed plan atomically and requires a fresh successful postcheck. Supabase's actual owning administrator/support could execute `providerAdminStatements` to remove these defaults completely; ordinary `postgres` must not attempt to impersonate or grant itself the unavailable provider administrator. Keeping the defaults behind denied schema access is a narrowly reviewed fallback, not general permission to ignore defaults or weaken table privileges.

The exact managed-schema allowlist is `auth`, `storage`, `realtime`, `extensions`, `graphql`, `graphql_public`, `supabase_functions`, `supabase_migrations`, `vault`, `net`, `cron`, `pgbouncer`, `pgsodium`, and `pgsodium_masks`; `pg_*` and `information_schema` are system catalogs. Present managed namespaces are returned with their owner and `provider-managed-separate-review-required` assessment. They are neither blanket-revoked nor represented as verified by application containment. Root/provider review must assess managed Auth/Storage/GraphQL policies and callable paths separately. A familiar namespace name is a classification, not proof that its objects are safe. Explicit global default ACL changes are listed by owner because they affect that owner's future objects in managed as well as application namespaces and require review. No managed schema or privilege was mutated in this follow-up.

The explicit CLI is `bun packages/neuvetra-database/src/staging-operator.ts <action>`, with actions `audit`, `containment-plan`, `migrate`, `provision <private-roster-json>`, and `revoke <UUID>`. It reads only named operator settings: `NEUVETRA_STAGING_MIGRATION_DATABASE_URL`, `NEUVETRA_STAGING_PROJECT_REF`, `NEUVETRA_STAGING_REUSE_EXISTING=confirmed` for the existing project, and `NEUVETRA_STAGING_TARGET_CONFIRMED=synthetic-test-data` for mutations. It never prints credentials or raw driver failures. Its privileged URL permits only the matching `postgres` direct endpoint or session pooler on 5432, with verified TLS.

`migratePrivateStaging(db,{expectedProjectRef,syntheticTargetConfirmed:true,reuseExistingProject?})` takes an advisory transaction lock and either installs all migrations on an empty workflow namespace or verifies an exactly matching recorded baseline. An unknown/existing unversioned namespace, changed checksum or target mismatch fails closed; no automatic adoption/repair occurs. Real provider `auth.users`, `auth.uid()` and standard authenticated role must already exist. The dedicated runtime role is initially NOLOGIN; the authorized operator separately assigns its password and LOGIN through a protected channel. The web service receives only that runtime credential, never the migrator credential.

`provisionStagingRoster` consumes `{expectedProjectRef,workspaceId,ownerUserId,members:[{userId,role:'admin'|'member'}]}` containing explicitly approved existing Auth UUIDs. It validates all subjects in the same target, creates the fixed synthetic workspace once, installs authoritative memberships and active access, and revokes omitted members from that workspace's active roster. It refuses moving a subject to another company's approved roster and preserves history. Revocation changes only active access. Keep roster files outside Git; no invite email is sent by this package.

Company UUIDs and authoritative memberships are the current account boundary. There is no customer/payment/entitlement implementation; future billing must bind server-owned account/company IDs and never accept client writes as payment or access authority. The staging roster deliberately permits one approved workspace per subject; broader multi-company membership is future work.
