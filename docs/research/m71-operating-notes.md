# M71 operating boundaries

M71 is a saved **synthetic coverage register**, integrated into the existing private application. California reporting is the first product focus. A company's relevant operations elsewhere can be recorded and remain visible when methods, control facts or evidence are unsupported. This does not implement another jurisdiction's reporting product.

## Persistence and review

The server derives the acting user from authentication and checks current workspace admission and membership inside the database transaction. Saved corrections append versions; earlier contributors cannot review a successor. Review is bounded internal acceptance or a request for changes. It never establishes complete coverage, released methods, legal applicability or external assurance.

The coverage export is retained at save. Later review decisions are shown separately and do not alter the earlier download. Readback checks the snapshot, hashes, lineage, native columns, request provenance, audit and retained export bytes. Failed integrity checks withhold the register.

The fictional demonstration has bounded storage: at most 40 versions, 50,000 UTF-8 bytes per canonical snapshot and 3,800,000 total retained export bytes, with response space reserved for reviews and the envelope. A capacity refusal leaves earlier versions available. These are demonstration limits, not a customer-scale storage design.

## Local verification

Use isolated loopback PostgreSQL fixtures, an exact verified schema-14 baseline and canonical migration 0015. Preserve earlier fixtures when migration bytes change; never rewrite their receipts. Independent reviewers test native API behavior, tenant and revocation boundaries, corruption refusal and restoration. Browser verification uses the real register component and PostgreSQL-backed staging server with explicitly labeled fictional actors. It does not establish hosted authentication or deployment.

The temporary preview entry point and actor selector live outside published application outputs. The dedicated production image has an explicit source/migration allowlist; the local selector is excluded. Existing M63–M68 screens remain part of the private application.

## Existing-host deployment gate

Publishing reviewed code to rolling draft PR5 does not change the running service or hosted database. Before a hosted rollout:

1. Recheck the actual existing Railway service, source branch/head, successful deployment and Supabase project identity. Historical observations are not current proof.
2. Verify all 14 hosted migration receipts against the canonical manifest, inventory existing rows/roles and create a private recoverable backup. Verify recovery without altering the live baseline.
3. Apply only the reviewed additive 0015 migration through the existing operator connection with TLS verification. Preserve a durable migration receipt and old-row checks. Do not load the unrelated ENV export.
4. Build and deploy the exact reviewed rolling-PR head on the existing service, with schema-15 readiness and the same private authentication boundary. Check signed-out refusal and signed-in synthetic save, correction, distinct review and earlier export.
5. If deployment fails, retain all data and use the verified compatible prior image where possible. Do not drop the new tables or overwrite migration receipts as a rollback shortcut.

No M71 hosted rollout is established by the local tests or by this plan. No paid model request, new provider, customer upload, source release or calculation method is part of this milestone.
